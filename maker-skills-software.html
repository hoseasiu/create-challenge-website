Software

Software-focused projects in the CRE[AT]E Challenge typically take one of four forms:

  • Web/webapp — public or just for the co-designer
  • Desktop software — non-web
  • Mobile app — iOS or Android
  • MCU/SBC software — for microcontroller units (like Arduino or BeagleBone) or single-board computers (like Raspberry Pi or NVIDIA Jetson) to interface with sensors and actuators

Collaboration

Version Control

GitHub is a code repository for tracking changes and collaborating, and can host websites via GitHub Pages. The GitHub Student Developer Pack provides access to many additional resources.

Teams writing significant code should use GitHub for version control.

Design

User Interface and Front-End Development

Teams must consider the user interface regardless of whether the product has a visual interface. Some interactions are self-contained, like a desktop skill-practice app, while others involve the user, the software, and the external environment, like medication reminders or clothing-choice aids.

For software with a visual UI, think about what "pages" or states the user moves through and how they transition between them. Figma is a popular app for creating framework prototype mockups (wireframes) of an app or website without building all the features. It's free for students and educators and is recommended as a starting point for prototyping front-ends.

Non-Web Applications

Desktop Software Development

Desktop development is the most general kind of software development, with the broadest set of resources available.

Packaging

Packaging bundles software — executables, libraries, configuration, and metadata — into a structured format for deployment. For example, .msi, .exe, or .msix on Windows, or .dmg on macOS.

Why packaging matters

  1. Different environments — a development machine has the right libraries installed, but a user's laptop likely doesn't
  2. Dependency management — packaged apps detail their dependencies
  3. Consistent installs — uniform behavior across users, supporting automation, version control, and clean uninstalls
  4. Security & isolation — modern formats like MSIX on Windows grant package identity for system services, such as notifications

Apps

Mobile Application Development

iOS Development

Currently behind significant barriers:

  1. Must own a Mac for development
  2. An Apple Developer Account is required ($99/year per user)
  3. Must know Swift or Objective-C

Unless your team is already familiar with iOS development and willing to pay the costs, we recommend building a webapp instead that the co-designer can access from their phone.

Android Development

Far more accessible: you can develop on any computer using Java or Kotlin. See the Android Developers getting-started guide and CodingWithMitch for tutorials and example projects.

Visual Programming for Mobile: MIT App Inventor

MIT App Inventor is an intuitive, visual (drag-and-drop) programming environment for building fully functional apps for Android phones, iPhones, and tablets — though iOS still requires a developer license to deploy.

Best for:

  • Rapid Prototyping — quickly create and test app ideas without extensive coding skills
  • IoT and Hardware Integration — connects mobile apps with Arduino or Raspberry Pi for sensor data, home automation, or remote control

  • Documentation
  • App of the Month Gallery

Inclusive Design

Software Accessibility Considerations

Check that images have descriptive alt text for screen-reader accessibility. Color and contrast are also important for low-vision and colorblind users.

  • Adobe's article on color contrast for accessibility
  • randoma11y.com — generates accessible color palettes with contrast checking
  • accessiBe's accessScan — checks a website's WCAG compliance
  • Firefox has a built-in colorblindness simulator in its Accessibility Inspector

Emerging Tools

AI and Machine Learning Tools for Accessibility

AI/ML tools are increasingly popular for student projects.

The Machine Learning Lifecycle — a video covering the machine learning life cycle from initial conception to deployment.

HuggingFace is a common platform for getting trained ML models and datasets — see their documentation page to get started.

Data Bias and Disability

A critical consideration in AT: dataset biases may work against you. For example, consider emotion recognition via computer vision for autism or neurodivergence. If you're recognizing the emotions of neurotypical individuals, standard datasets work. But if you're recognizing the emotions of your specific co-designer, public datasets may be insufficient, and fine-tuning with co-designer-specific data may be necessary.

Rule of Thumb

If the model's input is not affected by the co-designer's disability (for example, household objects), public datasets may be fine. If the input is affected by the disability (for example, facial expressions or vocalizations), you likely need co-designer-specific fine-tuning.

Example: The OpTECHs used visually identifying Uno cards and collected dataset data from their school.

Training Models

Don't train from scratch unless necessary — try to get an existing model and use it (see HuggingFace above). For fine-tuning, data collection, and labeling, you can do manual annotation on your own computer, or use CVAT, an online platform for dataset annotation, or Teachable Machine, a graphical interface for annotating datasets and automated workflows.
